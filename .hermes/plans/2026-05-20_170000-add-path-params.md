# Plan: 添加路径参数(Path Parameters)功能

## Goal

在 Hoppscotch REST 请求编辑器中，新增"路径参数(Path Parameters)"Tab，让用户可以通过 UI 直接设置 URL 路径中的变量（如 `/users/:id` 中的 `id`），无需手动在环境变量中配置。请求发送时，路径参数会自动替换 URL 中对应的占位符。

## Current Context

### 现状
- Hoppscotch 当前支持在 URL 中使用 `<<variable>>` 语法引用环境变量
- URL 路径变量（如 `/api/users/:id` 或 `/api/users/{{id}}`）只能通过环境变量间接替换
- RequestOptions.vue 中的 Tab 列表为：Params | Body | Headers | Authorization | Pre-request Script | Tests | Variables
- "Params" Tab 是查询参数(Query Parameters)，与路径参数无关
- "Variables" Tab 是请求变量(Request Variables)，用于在脚本中引用，不参与 URL 替换
- `parseTemplateString()` 用 `<<key>>` 正则替换环境变量

### 现有数据模型
- `HoppRESTRequest` (v17) 包含：endpoint, params, headers, body, auth, requestVariables 等
- `params` 字段 = `HoppRESTParams` = `Array<{key, value, active, description}>` — 这是查询参数
- `requestVariables` = `Array<{key, value, active}>` — 请求变量（用于脚本）
- **无 pathParams 字段**

### 路径变量替换机制
- `getEffectiveRESTRequest()` (EffectiveURL.ts) 调用 `parseTemplateString(request.endpoint, environment.variables)` 
- 只替换 `<<var>>` 格式的环境变量，不会处理 `:id` 或 `{id}` 格式

## Proposed Approach

### 核心思路
在 HoppRESTRequest 数据模型中新增 `pathParams` 字段，新增 PathParams Tab UI，在请求执行时将路径参数合并到环境变量中参与 `<<key>>` 替换。

**路径参数的 URL 格式**：使用 `<<key>>` 语法（与现有环境变量一致），用户在 URL 中输入 `https://api.example.com/users/<<user_id>>`，在 Path Params Tab 中设置 `user_id=123`，请求时自动替换。

### 为什么不用 `:id` 格式
- 需要修改 `parseTemplateString` 核心逻辑，风险大
- `<<key>>` 格式已成熟，UI 提示更友好
- 与环境变量机制完全一致，无额外解析负担

## Step-by-step Plan

### Step 1: 数据模型 — 新增 pathParams 字段 (hoppscotch-data)

创建新版本 v18，在 HoppRESTRequest 中添加 `pathParams` 字段。

**文件变更：**

1. **新建** `packages/hoppscotch-data/src/rest/v/18.ts`
   ```ts
   import { z } from "zod"
   import { defineVersion } from "verzod"
   import { V17_SCHEMA } from "./17"

   export const HoppRESTPathParams = z.array(
     z.object({
       key: z.string().catch(""),
       value: z.string().catch(""),
       active: z.boolean().catch(true),
       description: z.string().catch(""),
     })
   )

   export type HoppRESTPathParams = z.infer<typeof HoppRESTPathParams>

   export const V18_SCHEMA = V17_SCHEMA.extend({
     v: z.literal("18"),
     pathParams: HoppRESTPathParams,
   })

   export default defineVersion({
     schema: V18_SCHEMA,
     initial: false,
     up(old: z.infer<typeof V17_SCHEMA>) {
       return {
         ...old,
         v: "18" as const,
         pathParams: [],
       }
     },
   })
   ```

2. **修改** `packages/hoppscotch-data/src/rest/index.ts`
   - import V18_VERSION
   - latestVersion: 18
   - versionMap 添加 `18: V18_VERSION`

### Step 3: 请求执行 — 合并路径参数到环境变量 (hoppscotch-common)

修改 `getEffectiveRESTRequest()` 将 pathParams 作为临时环境变量注入。

**文件变更：**

1. **修改** `packages/hoppscotch-common/src/helpers/utils/EffectiveURL.ts`
   - 在 `getEffectiveRESTRequest()` 中，将 `request.pathParams` 中 active 的项转换为临时环境变量
   - 合并到 `environment.variables` 中（pathParams 优先级高于全局环境变量，低于请求级环境变量）
   - 确保 `effectiveFinalURL` 的 `parseTemplateString` 能解析到这些变量

   ```ts
   // 在 getEffectiveRESTRequest 中添加：
   const pathParamVariables = pipe(
     request.pathParams ?? [],
     A.filter((x) => x.active && x.key !== ""),
     A.map((x) => ({
       key: x.key,
       value: x.value,
       secret: false,
     }))
   )

   // 合并环境变量（pathParams 优先）
   const mergedVariables = [
     ...pathParamVariables,
     ...environment.variables.filter(
       (v) => !pathParamVariables.some((p) => p.key === v.key)
     ),
   ]

   const mergedEnvironment = { ...environment, variables: mergedVariables }
   ```

2. **修改** `packages/hoppscotch-common/src/helpers/RequestRunner.ts`
   - 在 `resolveEnvVars` 中将 pathParams 注入环境变量解析

## Tests / Validation

1. **数据模型测试**：创建 v18 请求，验证 pathParams 序列化/反序列化
2. **迁移测试**：v17 → v18 升级，确认 pathParams 默认为空数组
3. **URL 替换测试**：设置 pathParams `[{key:"id", value:"123"}]`，URL `https://api.com/users/<<id>>`，验证替换为 `https://api.com/users/123`
4. **优先级测试**：pathParams 与环境变量同名时，pathParams 优先
5. **UI 交互测试**：在 Path Params Tab 添加/删除/禁用参数，验证 Tab 计数和 URL 变化
6. **E2E 测试**：导入含路径参数的 cURL，发送请求，验证完整流程

## Risks & Tradeoffs

1. **Schema 版本升级**：v18 是破坏性变更，旧版本客户端无法读取。但由于是 fork 版本(dev分支)，风险可控
2. **路径变量格式**：选择 `<<key>>` 而非 `:key` 或 `{key}` 是为了复用现有解析逻辑，但不如 `:key` 直观（Postman/Swagger 用 `:key` 或 `{key}`）
3. **自动检测**：URL 中输入 `<<var>>` 自动添加 pathParams 行可能导致误触发，需考虑去重和用户意图
4. **向后兼容**：旧请求没有 pathParams 字段，v18 迁移会添加空数组，兼容
5. **GraphQL schema 迁移**：如果后端也有对应 schema，需要同步更新后端

## Open Questions

1. **路径变量格式选择**：是否需要同时支持 `:key`、`{key}` 和 `<<key>>` 三种格式？还是只支持 `<<key>>`？
2. **pathParams 与环境变量优先级**：pathParams 是否应该覆盖同名环境变量？（当前方案是覆盖）
3. **URL 自动检测时机**：实时检测（每次输入）还是失焦后检测？实时可能性能问题
4. **是否需要路径变量高亮**：URL 输入框中是否需要对 `<<pathVar>>` 做不同颜色高亮以区分环境变量？
