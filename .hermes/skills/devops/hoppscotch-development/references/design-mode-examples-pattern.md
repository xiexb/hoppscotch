# Design Mode Examples — Unified Tabs Pattern

## Architecture

Both **RequestBodySection** (request body) and **ResponseSection** (response body) use the same unified examples pattern:
- Virtual default example (auto-generated from schema tree, NOT stored)
- Stored examples (user-created, persisted in `bodyExamples[]` / `responseModels[].examples[]`)
- Tab-based UI that treats both identically

## Virtual-to-Stored Materialization

```
effectiveExamples computed:
  ├─ stored examples exist? → return stored
  └─ no stored? → return [{ name: "Default Example", body: autoGenerated }]  (virtual)
```

**Materialization triggers** (virtual → stored):
1. User edits content → creates stored array with edited content
2. User renames (dblclick tab) → creates stored array with new name
3. User adds new example → materializes default + appends new

**Key principle:** Virtual examples are never stored until the user interacts with them. The computed `effectiveExamples` always returns a non-empty array for the UI to render.

## Tab UI Pattern

```vue
<!-- Example selector tabs (shown when >1 example OR has stored examples) -->
<div class="flex items-center gap-1 overflow-x-auto mb-2 border-b border-dividerLight pb-1">
  <button
    v-for="(ex, exIdx) in effectiveExamples"
    :class="activeTab === exIdx ? 'border-b-2 border-accentLight font-bold' : 'text-secondary'"
    @click="activeTab = exIdx"
    @dblclick="startRename(exIdx)"
  >
    <template v-if="renamingIndex === exIdx">
      <input v-model="renamingName" @keyup.enter="confirmRename(exIdx)" @keyup.escape="cancelRename" />
    </template>
    <template v-else>
      <span>{{ ex.name }}</span>
      <button v-if="effectiveExamples.length > 1" @click.stop="deleteExample(exIdx)">×</button>
    </template>
  </button>
</div>

<!-- Active example content (always editable) -->
<JsonExampleBlock
  :content="activeExampleBody"
  :content-type="activeContentType"
  :editable="true"
  @update:content="onContentUpdate"
/>
```

## Beautify/Format Button

`JsonExampleBlock.vue` has a ✨ sparkles icon button in the preview toolbar (next to the copy button):
- **JSON**: `JSON.parse()` then `JSON.stringify(parsed, null, 2)` — validates and reformats with 2-space indent
- **XML**: Custom `beautifyXml()` function — normalizes whitespace between tags, adds proper indentation
- Emits `update:content` with the formatted result (persists the change to the data model)
- Shows toast: success ("已美化" / "Formatted!") or error ("JSON格式无效" / "Invalid JSON")
- Works for both editable and read-only blocks — beautify always modifies content

**i18n keys** (in `json_example_block` namespace): `beautify`, `beautified`, `invalid_json`, `unsupported_format`

## Preview Mode Sync

PreviewView reads from the same data arrays:
- Request body: `request.bodyExamples` (same array as edit mode)
- Response: `responseModels[idx].examples` (same array as edit mode)

When no stored examples exist, PreviewView generates from schema tree using `generateExampleFromSchema()` / `generateJsonFromSchemaTree()` / `generateXmlFromSchemaTree()`.

**Auto-sync:** No explicit sync mechanism needed — both edit and preview read from the same reactive `props.request` data. Changes in edit mode automatically appear in preview mode.

## Data Model Fields

### Request body examples
```typescript
// HoppRESTRequest (v22+)
bodyExamples: HoppRESTBodyExample[]  // stored examples (empty = use virtual default)

interface HoppRESTBodyExample {
  name: string
  body: string
  contentType: string  // "application/json" | "application/xml" | etc.
}
```

### Response examples
```typescript
// HoppRESTResponseModelV23
examples: HoppRESTResponseExample[]  // stored examples (empty = use virtual default)
bodyExample: string  // backward compat: first example body (kept in sync)

interface HoppRESTResponseExample {
  name: string
  body: string
}
```

## Pitfalls

### Don't make default example read-only
The original design had the default example as read-only (`:editable="false"`) with a separate "auto" badge. User corrected: default example should be editable and renamable like any other. The "auto" badge only shows when examples are virtual (not stored).

### Duplicate name validation must exclude self
When renaming, check `existing.some((ex, i) => i !== index && ex.name === newName)` — excluding the current index. Without this, renaming to the same name triggers a false duplicate error.

### Content type follows request body, not per-example
For request body examples, the content type is `request.body.contentType` (JSON/XML). Individual examples can have their own `contentType` field for flexibility, but the default follows the request body type.

### XML example generation uses different function
JSON examples use `generateJsonFromSchemaTree()` → `generateExampleFromSchema()`. XML uses `generateXmlFromSchemaTree()` which has its own tree walker with `escapeXml()` and `sanitizeXmlTag()`. Both support `modelResolver` for expanding `modelRef` nodes.

### Tab selected-state uses text-accent, not text-primary
The active example tab MUST use `border-b-2 border-accent font-semibold text-accent` — NOT `text-primary` (which renders white/invisible on light backgrounds). This is a user-corrected pattern that applies to ALL tab-style UIs in the design mode (request body examples, response examples, response model tabs).

### Reset activeExampleTab when switching contexts
- ResponseSection: reset `activeExampleIdx` when switching response model tabs (via `watch(activeModel, () => { activeExampleIdx.value = 0 })`)
- PreviewView: reset `activeExamplePreviewTab` when switching response tabs
- RequestBodySection: no context switch (single body), but reset after delete if tab index exceeds new length
